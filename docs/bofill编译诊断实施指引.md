# 下一阶段任务：bofill 编译退化定位、求解修复与性能验证

## 一、总体要求

基于 GitHub 仓库 `https://github.com/ChenKaichen-SCUT/lia_cover_sampler` 的冻结提交 `a31e91e` 创建新分支 `bofill-compiler-diagnosis`。

本轮目标不是继续扩大表示变换规模，而是通过受控消融和源码级诊断，明确以下问题：

1. SMT_random 编译版为什么在900秒内没有生成任何模型？
2. SMT_real 编译版为什么首次求解比普通版慢约一个数量级？
3. 性能退化主要来自整数选择编码、等式消元、反复简化，还是短超时查询与公式表示的相互作用？
4. 当前编译器为什么在200万次操作限制下，仅完成random的2次、real的33次单位等式消元？
5. 能否在保留原始 OR 结构的情况下，通过更有针对性的等式处理获得实际性能收益？
6. 如何防止可选编译机制再次让原本能够采样的公式变成长期零输出？
7. 在修复求解退化之后，是否真正提高固定时间及固定样本数的覆盖，而不是仅增加模型数量？

**本轮采用分阶段实验。先完成原因分析和最小修复，不直接启动新一轮900秒实验。** 只有短预算实验获得明确正面结果，才执行限定规模的后续验证。不得通过不断增加时间、修改参数或更换实例寻找正面结果。

保留上一轮 `results/bofill_900s/`、历史源码和原始审计数据，不覆盖、不修改已有报告和实验结论。

不重跑HighDiv，不启用已淘汰的投影生成、宏观指定分支、变量块扩张或其他旧实验机制。

## 二、第一阶段：将编译过程拆成独立可测的变换

### 2.1 修改现有编译器

重点修改：

```text
include/lia_choice_compiler.hpp
src/lia_choice_compiler.cpp
src/bofill_sampler.cpp
```

目前 `Compiler::run()` 固定执行：

```cpp
flatten(f.root, clauses);
encode_choices();
eliminate();
```

改成支持以下五种明确配置：

| 配置 | 选择编码 | 单位等式消元 | 其他处理 |
|---|---|---|---|
| `plain` | 不启用 | 不启用 | 原始公式 |
| `simplify_only` | 不启用 | 不启用 | 对完整原公式执行一次明确记录的简化 |
| `eq_only` | 不启用 | 启用 | 保留原始 OR |
| `choice_only` | 启用 | 不启用 | 当前整数0/1选择编码 |
| `full` | 启用 | 启用 | 复现上一轮完整编译 |

保留历史 `choice_compiled` 名称作为 `full` 的兼容别名，但输出日志必须写明实际配置，不允许混淆。

五种配置共用相同求解器、随机种子、模型恢复、验证、阻塞和输出逻辑。

`eq_only` 必须直接处理原始公式的全局必要等式，不得先隐式执行 `encode_choices()`。

`choice_only` 不得执行任何单位等式消元。

`simplify_only` 用于检查公式简化本身的影响，不能暗中调用选择编码或消元；具体调用的 Z3 简化参数要记录。

所有模式都应使用原始公式进行覆盖统计，不能改变原 AST、原变量身份、短路访问和整数低64位指标。

### 2.2 增加中间表示导出

每个变换阶段保存独立的求解公式：

```text
original.smt2
simplified.smt2
choice_only.smt2
eq_only.smt2
full.smt2
```

同时导出对应的完整模型恢复映射。

对每份公式记录：

```text
原变量数
新增辅助变量数
当前求解变量数
OR/AND数量
等式、不等式数量
变量乘常数的出现数量
二元选择组数量
整数系数大小分布
原始与编译后DAG节点数
必要等式图的连接关系
恢复表达式DAG大小
预处理耗时与停止原因
```

注意：不能仅凭“最大数值位数”判断算术难度。必须分析选择变量进入了多少算术表达式，以及它们形成了怎样的约束关联。

结构统计是描述性证据，不得直接把某个结构数量视为 Z3 的实际求解成本。

## 三、第二阶段：细分编译器的真实开销

### 3.1 精确统计每个编译阶段

当前每次改写都可能全局执行 `substitute()`、`simplify()` 和 DAG 扫描，导致操作额度较早耗尽。

对下面几个步骤独立计时并计数：

```text
flatten
选择组识别
选择组替换
单位等式候选搜索
表达式线性化
引用次数扫描
全式 substitute
全式 simplify
恢复映射更新
联合DAG检查
```

至少记录：

```text
每个阶段进入次数
扫描节点数
操作计数
实际墙钟时间
成功提交的改写次数
因预算、增长或不支持而跳过的次数
每次改写前后的DAG规模
```

对于每一次单位等式消元，记录选择原因、替换宽度、预计表达式增长、真实增长和处理时间。

### 3.2 判断为什么只有2次或33次消元

必须区分以下原因：

- 没有更多合法的单位系数消元候选；
- 有候选，但因引用次数或表达式增长限制被排除；
- 候选搜索和重复扫描消耗过多操作；
- 前面的选择编码改变了原本可消元的结构；
- 部分简化使等式不再符合当前识别器；
- 尚有候选，但200万次操作限制提前停止。

输出每种原因的数量和实际证据。

**不要直接把200万操作上限改成2000万，然后声称修复完成。**

若是算法反复扫描造成的浪费，才考虑引入有界工作队列、反向依赖索引或受影响子句的增量重新分析。

优化后的消元程序必须与旧版本使用相同的合法性条件和恢复语义。不能在优化扫描时改变可消元变量集合，又把性能差异全部归因于扫描加速。

### 3.3 采用事务式、可回退的增量更新

若诊断确认重复全式扫描是主要瓶颈，实现一个可独立切换的增量版本：

- 维护变量到相关子句的反向引用；
- 一次消元后只更新确实依赖该变量的约束；
- 更新受影响的候选等式及其引用次数；
- 恢复表达式继续保持完整且正确；
- 不能局部判断安全后遗漏全局增长或预算检查。

增量版本与原完整扫描版本必须通过相同的模型恢复、等价性和资源限制回归。

如果诊断显示主要瓶颈不是扫描，暂不实现增量工作队列，以免增加无效复杂性。

## 四、第三阶段：检查真实实例上的变换正确性

当前小型公式回归已经证明了很多局部规则，但 SMT_random 编译版900秒没有输出模型，因此这次必须补充真实实例上的具体语义核验。

### 4.1 使用已有合法模型验证提升和恢复

从上一轮 `plain_clean` 的原始归档中，按固定顺序读取两个公式各自前10个已经独立验证的合法模型。

对每一种编译配置，检查：

$$
F(m)=\mathrm{true},
$$

$$
F_c(\operatorname{lift}(m))=\mathrm{true},
$$

以及：

$$
\operatorname{restore}(\operatorname{lift}(m))=m.
$$

逐个原变量比较，使用精确整数，不允许浮点近似。

复用已有 `CompiledProblem::lift()` 和 `restore()`，但是测试必须重新评价编译公式，而不是只比较恢复赋值。

这些历史模型只能用于正确性诊断，不能作为后续性能实验的初始模型或求解器提示。

### 4.2 检查选择变量是否真实受到正确约束

对于每个被引入的选择变量，验证：

```text
取值范围
对应原变量恢复表达式
原二选一组是否正确消除
所有其他使用原变量的约束是否同步代入
是否遗漏剩余原变量引用
```

检查重叠选择组、条件 OR、同名辅助变量、负整数和大整数。

若发现实际公式上的恢复错误或变换不等价，首先修复正确性，再进行求解性能实验。

如果所有历史见证均成功提升和恢复，只能说明这些具体赋值通过检查，不能宣称已经用有限样本证明一般等价性。

保留小型有界公式的完整模型集合对照测试。

## 五、第四阶段：独立研究短查询与连续查询的影响

这是本轮必须完成的关键实验。

### 5.1 现有问题

上一轮 SMT_random 编译版900秒内进行了452次 `check()`，绝大多数单次上限为2000毫秒，全部 Unknown。

需要检验两种可能性：

**假设 A：** 编译公式本身难求，即使给出较长连续求解时间，仍然明显慢于原公式。

**假设 B：** 编译公式与反复限时取消之间存在不利的相互作用；较长的单次查询可能表现不同。

不能预先认定哪一种成立。

### 5.2 新增首次 SAT 诊断入口

建议新增：

```text
src/bofill_first_sat_probe.cpp
```

该入口只测首次求解，不枚举大量样本。

支持两种求解控制：

**模式一：`repeated_2s`**

按照当前分级策略：

```text
50 → 200 → 1000 → 2000 ms
```

随后继续按2000毫秒上限重复 `check()`，直到找到首个模型或总预算结束。

**模式二：`continuous`**

使用相同类型的新求解器、相同随机种子和相同编译公式，执行一次连续的首次 `check()`，其上限为扣除预处理与日志成本后的剩余预算。

两种模式每个会话总预算完全相同。

不能将重复查询累计30秒与连续查询只有2秒进行对比，也不能把编译或公式加载免费排除。

### 5.3 第一批诊断实验

固定：

```text
2个实例
× seed 0、1
× 5种编译配置
× 2种求解控制
= 40次首次SAT诊断
```

每次总预算30秒，最多四路并发，按完整配对分批执行。

所有配置统一：

```text
Z3版本
solver类型
random_seed
逻辑与参数
构建优化级别
CPU资源
内存限制
完整计时起点
```

运行前冻结计划、哈希和参数。

如果没有找到模型，记录为 `NO_SAT_WITHIN_BUDGET`，不能写成 UNSAT。

保存每次查询的：

```text
raw SAT/UNSAT/Unknown
reason_unknown
实际请求与授予的timeout
纯check耗时
约束构造与预处理成本
总CPU/墙钟
首次SAT时刻
模型恢复和原公式验证
```

### 5.4 记录Z3求解器统计

利用当前 Z3 API 导出求解器公开的 statistics，包括实际可获得的：

```text
conflicts
decisions
propagations
restarts
arith相关统计
memory
```

统计名称取决于实际 Z3 构建，必须枚举真实可用项并保留原始名称，不得虚构缺失指标。

记录统计时的求解器状态和时间，统计读取本身的开销也要计入诊断预算。

重点检查是否存在：

- 某一种表示导致冲突与决策数量明显上升；
- 整数算术推理成本显著变化；
- 长连续查询和短重复查询的行为差异；
- 求解器持续 Unknown 却没有有效搜索进展。

即使统计显示某项算术活动增加，也只能作为解释性能差距的证据，不能直接断言它是唯一因果原因。

### 5.5 有限延伸诊断

若30秒仍无法区分原因，可以针对**预先指定的 SMT_random、seed 0**，增加一组原式与完整编译式的120秒连续首次求解对照。

这只是诊断，不扩大到所有配置和全部种子，不自动执行900秒。

如果连续120秒仍无编译SAT，记录失败，不继续依次增加到300、600、900秒。

## 六、第五阶段：按照诊断结果选择修复方向

本阶段必须根据前四阶段的结果作出选择，不能同时实现所有备选改进。

### 情况 A：`choice_only` 已明显退化，`eq_only` 正常

说明选择算术化是主要嫌疑。

处理：

1. 停止将二选一 OR 默认转换为整数0/1变量。
2. 保留原始显式 OR。
3. 只继续研究有证据支持的等式化简。
4. 如果 `eq_only` 的首次求解也没有实际优势，就不继续推进消元优化。
5. 报告为何现有结构下变量减少却没有降低求解成本。

不自动再尝试更复杂的选择变量组合或强制分支策略。

### 情况 B：`eq_only` 明显退化，`choice_only` 正常

重点检查：

```text
消元变量的选择顺序
消元是否扩大约束关联
恢复表达式是否变复杂
是否消去了有利于求解器传播的中间变量
```

优先限制导致实际求解困难的消元，而不是增加消元数量。

必要时保留关键中间变量，只有当变量替换没有明显增加约束连接和求解成本时才消去。

任何新的选择规则必须在性能验证前冻结。

### 情况 C：两种独立变换都正常，但 `full` 退化

说明可能存在变换之间的负面相互作用。

检查选择编码之后的新辅助变量是否进入单位等式消元，是否形成更大约束，以及最终求解公式与两个独立变换之间的差异。

不要直接将 `full` 改成“更多消元”；优先选择实际表现较好的独立变换，或禁止已确认不利的组合步骤。

### 情况 D：只有 `simplify_only` 已经退化

说明公式简化和重写形式可能改变了求解器行为。

停止对整份公式反复调用通用 `simplify()`，检查是否可以保留原语法结构，仅在必要的局部表达式上进行语义保持的化简。

### 情况 E：连续首次求解成功，重复2秒查询失败

说明当前预算策略与该公式存在明显交互。

修复首次求解控制：首次SAT之前允许一段有界连续查询，之后再使用适合增量枚举的短查询。

必须比较同样预算下原公式是否也得到相同收益。

不能因为编译公式需要更长时间，就只给编译版额外预算而不给普通版相同机会。

### 情况 F：所有编译配置都不如原公式

明确停止该编译优化方向的性能扩展。

保留原式作为默认求解表示，保留正确性实现和负实验记录，不再通过增加操作上限或改写更多变量寻找收益。

## 七、第六阶段：加入安全回退，修复“可选优化导致900秒零输出”

无论具体原因是什么，后续不能让一种可选编译机制无条件占用全部900秒。

在完成原因隔离后，新增实验性安全回退机制，例如：

```text
编译后的求解器启动
        ↓
在预定首次SAT预算内尝试
        ↓
及时获得合法模型？
        ├── 是：继续当前求解流程
        └── 否：停止编译求解器
                ↓
              构造原公式求解器
                ↓
              在剩余总预算内继续采样
```

推荐首版使用统一的10秒首次模型回退阈值，作为固定工程保护，不对两个公式采用不同阈值。

但该阈值不是经过验证的最优值；若诊断显示一个潜在有价值的变换正常首次求解需要更长时间，应先通过公平实验评价这种选择，而不是为了让它成功而事后调整阈值。

全部编译、失败求解、原求解器初始化和回退成本计入总时间。

回退不得使用历史模型作为种子，也不得把编译阶段的非证明 Unknown 当成原公式不可满足。

如果编译阶段已经正式输出模型，后来因其他原因回退，必须保留正式覆盖与去重状态，并在原求解器上排除已经输出的完整原赋值。

新模块应分别报告：

```text
编译表示自身的成功率与收益
安全回退发生次数与成本
回退后的普通探索收益
完整策略的端到端覆盖
```

不能把普通回退产生的覆盖归功于编译器。

在没有性能正证据前，`plain` 继续作为默认模式；安全回退只作为实验性保护。

## 八、第七阶段：短时间验证候选改进

只有前面的诊断找到明确且正确的修复候选，才启动新的在线采样实验。

### 8.1 候选数量限制

最多晋级**一种**编译或求解策略，避免五种模式同时进入新的长时间比较。

必须保留：

```text
plain_clean
best_diagnosed_variant
```

如果尚需检验安全回退，可增加：

```text
best_diagnosed_variant_with_fallback
```

但要分别报告纯变换和回退策略的贡献。

### 8.2 固定60秒在线验证

首先比较：

```text
2个实例
× seed 0、1、2
× 2个主要配置
= 12次60秒会话
```

如果需要第三配置，应在实验协议中事先说明，总数最多18次。

沿用相同完整模型阻塞、原公式验证、覆盖计算及截止处理。

必须报告：

- 首次合法模型时间；
- 60秒不同模型总数；
- 正增益正式样本数；
- 固定5、10、30、60秒的累计覆盖；
- 前2、5、10、50、100个不同样本的覆盖；
- 最长连续零收益段和无覆盖增长时间；
- 编译、首次求解、枚举、恢复、验证和输出的成本；
- 发生回退的时间、次数及后续收益。

未达到前缀的会话保留未完成，不能只统计成功输出的运行。

### 8.3 晋级要求

继续更长实验必须满足：

1. 两个公式均能够在预算内稳定产生首个合法模型，不能再出现一个公式长期零输出。
2. 相对于 `plain_clean`，首次求解时间不能在某个实例上出现大幅、可重复的退步而没有覆盖补偿。
3. 固定60秒的累计覆盖在至少两个种子上有正面信号，且不存在明显的跨种子严重退步。
4. 固定样本数下的覆盖不能持续下降；若收益只是更多模型带来的吞吐优势，需明确标记。
5. 完整成本和独立审计通过，回退成本不能隐藏。
6. 新算法收益必须与普通回退产生的收益分开归因。
