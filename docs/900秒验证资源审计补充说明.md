# 900秒验证：Z3超时辅助线程的资源审计修正

本说明补充 `原生干预位置900秒新seed冻结协议.md`，不修改其中的采样预算、CPU分配、算法、种子或统计规则。

正式运行中发现：冻结的 Z3 `scoped_timer` 创建一个等待超时的辅助线程。因此每个采样进程包含一个求解主线程及一个超时辅助线程，操作系统报告为2个线程。上一轮相同二进制的资源记录也显示2个线程。原新增审计错误地要求操作系统线程数不超过1，会将这种情况误判为增加求解并行度。

所有采样进程保持原来的单个逻辑CPU亲和性；其子线程继承该亲和性。资源观察器在两批运行期间为全部28个运行分别记录3份逐线程快照，保存CPU亲和性、状态、CPU时间计数与等待位置。观察器与原监督器共享CPU14，不占用采样工作CPU。采样仍是14路逻辑CPU并行，使用7个物理核心，不是14个独立物理核心。

修正位于独立文件 `scripts/complete_position_frozen_900s.py`。原审计、原冻结协议和计划均保留原样。收尾程序等待28次采样全部完成且原控制器退出，只在确认原错误确为 `multithreaded sampler`、所有冻结文件哈希一致时继续。它保留全部资源、配对和模型审计，并将错误的线程断言替换为：最多2个OS线程、每个线程均绑定该运行唯一分配的逻辑CPU、逐线程快照能够解释资源日志中的最大线程数。出现额外线程、逃逸CPU或证据缺失仍失败。

独立模型审计仍调用冻结的原始审计函数，逐模型使用 ManualSatisfiesMetric 核验；未修改覆盖计算、统计规则、已保存模型或历史数据。4项资源审计回归只在全部采样结束后执行。原错误日志和修正依据均随结果归档，不重跑任何采样。

证据位于 `results/position_frozen_900s/thread_audit_support/`，包括 `thread_samples.jsonl`、计时器源码副本及哈希、`correction.json` 和回归结果。`source.json` 绑定源码及冻结Z3库的哈希，`correction.json` 同时绑定原审计、新审计、原错误日志的哈希。

在采样结束、原始运行目录已经存在或从本轮归档恢复后，离线重放使用：

```bash
HIGHDIV_ROOT=/tmp/lia-highdiv-frozen PYTHONPATH=scripts:python \
  /tmp/lia-highdiv-frozen/venv/bin/python3 scripts/complete_position_frozen_900s.py \
  results/position_frozen_900s --audit-only
HIGHDIV_ROOT=/tmp/lia-highdiv-frozen PYTHONPATH=scripts:python \
  /tmp/lia-highdiv-frozen/venv/bin/python3 scripts/analyze_position_frozen_900s.py \
  results/position_frozen_900s
python3 scripts/plot_position_frozen_900s.py results/position_frozen_900s
```

上述命令只审计和分析保存模型，不启动求解器搜索。`--audit-only` 不启动采样、不自动推送。自动收尾模式具有进程锁，避免重复生成审计和归档。
