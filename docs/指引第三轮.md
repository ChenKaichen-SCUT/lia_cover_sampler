# LIA Cover Sampler 第三轮：执行效率修复与快速迭代实验指引

## 一、项目与修改范围

基于 GitHub 仓库：

https://github.com/ChenKaichen-SCUT/lia_cover_sampler

冻结基点为 `round2-control-and-lines` 分支的提交：

`21befad43206c4917104767138b9317740ecf9ae`

本轮目标是修复第二轮审阅确认的三个主要问题：

1. 调度器因软冷却导致计算资源闲置。
2. `Search::safe()` 和 `Search::line()` 预先进行大量方向、目标与可行域分析，却未及时生成候选。
3. `Search::polish_candidate()` 未合理分配多步改进预算，导致一次内部调用可能耗尽整个候选额度。

同时修复目标轮转扫描和全局目标空状态记录等低成本问题，并建立新的快速实验工作流，显著减少每次迭代的采样运行总成本。

**本轮不新增复杂算法框架，不修改 SMT 求解器内核，不重写已经验证的 GMP 模命中数学核心。**

保留：

- 原始 AST-bit coverage 定义及 HighDiv 评测器。
- 全部样本的合法性验证和完整类型赋值。
- 单模型改进期间正式覆盖状态只读的原则。
- 已经验证的 LineDomain 精确语义与结构等式作用域。
- 显式增量 SMT 探索求解器的正确性修复。
- 原始 HighDiv、第一轮 LIA 和第二轮全部实验结果。

所有修改在新分支完成，每个重要修改形成独立提交，可单独启用和关闭。不要直接覆盖现有冻结结果。

## 二、问题 1：消除调度器造成的无效等待

### 2.1 定位现有问题

重点检查：

`src/scheduler.cpp`

- `Scheduler::choose()`
- `Scheduler::feedback()`
- `Scheduler::refresh()`

以及：

`src/main.cpp`

- `scheduler.choose(...)`
- `if (!selection) { sleep_for(...); continue; }`
- 探索求解器自身 cooldown 与调度器 cooldown 合并的代码。

当前 `Scheduler::feedback()` 会在连续零覆盖收益后设置 `cooldown_until`。

当四个模块全部处于冷却时，`Scheduler::choose()` 返回空；主循环每次休眠 1 ms，直到某个模块冷却结束。

这会造成即使全局时间预算充足、仍有可以尝试的搜索动作，采样器也可能主动闲置。

上轮九例的墙钟合计约 8100 秒，父动作合计约 3716 秒。差额不能全部直接认定为休眠，但已经足以要求精确计时和调度修复。

### 2.2 区分软冷却与硬限制

将冷却状态区分为：

**SoftCooldown**

代表模块近期性价比较差，只降低优先级，不意味着禁止执行。

**HardUnavailable**

代表模块当前确实不能执行，例如整个预算结束、外部取消、需要等待某个明确的资源恢复条件。

不能把求解器一次 `Timeout` 或 `Unknown` 直接解释为永久不可执行。

调度规则修改为：

- 存在正常可用模块时，优先按近期收益和成本选择。
- 全部模块都处于 SoftCooldown 时，选择当前最有希望的模块执行一个受限动作。
- SoftCooldown 不应单独导致主循环休眠。
- 全部模块确实不可执行时，允许有界休眠，但必须记录原因和实际时间。
- 不得用无限的短时间重复调用代替休眠，否则可能导致 CPU 空转和大量无效操作。

尤其不能简单把所有 `cooldown_until` 永远设置成零。应保留收益驱动的优先级调节和困难求解的退避功能。

### 2.3 调度器必须保证工作保持性

在仍有总体时间预算、存在合法执行动作且未受到硬限制时，调度器必须选择某个动作，而不是返回空。

可以把调度接口改为返回：

```cpp
struct SchedulingDecision {
    ActionKind action;
    double allocated_seconds;
    bool bypassed_soft_cooldown;
    std::string reason;
};
```

如果所有动作都不具备执行条件，应返回明确的无动作原因，而不是无信息的 `nullopt`。

对长时间零收益的探索，仍允许降低优先级和缩小投入，不要求持续生成大量零覆盖样本。

### 2.4 补全时间核算

实现互不重复的顶层墙钟时间分解：

```text
total_wall_seconds
  parsing_and_initialization
  action_wall_seconds
  scheduler_decision_seconds
  idle_sleep_seconds
  checkpoint_and_logging_seconds
  other_wall_seconds
```

每个父动作内部再保留现有阶段统计，但不得把父动作与其子阶段重复相加。

使用单调时钟。所有休眠都通过统一封装函数进行计时。

报告：

```text
idle_fraction
soft_cooldown_bypasses
all_actions_soft_cooled
hard_unavailable_events
actions_selected_after_cooldown
```

要求报告中能够清楚解释第二轮约 4384 秒未完整分项的时间在新版本中对应什么，而不是直接假设它全部来自休眠。

### 2.5 回归测试

使用模拟时间和模拟动作结果构造以下场景：

1. 四个模块连续无新增覆盖，但仍然可以合法运行。
2. 某个模块持续产生不同模型但没有新增覆盖。
3. 某个模块收益很低，另一个模块后来开始取得正收益。
4. 所有模块确实受到硬限制。

验证：

- 软冷却不会导致长时间无动作。
- 低收益模块不会永久垄断时间。
- 高收益模块能够获得更多计算预算。
- 必要的硬限制依然生效。
- 顶层计时与真实墙钟时间一致，误差可解释。

完成这一阶段后，先只比较**控制修复 A/B 版本、新调度旧版本、新调度修复版本**，不要同时改变候选生成。

## 三、问题 2：局部生成改成流式 Anytime 算法

### 3.1 定位问题

重点检查：

`src/search.cpp`

- `Search::safe()`
- `Search::line()`
- `quota_directions()`
- `TargetManager::select()`

当前流程大致是：

```text
计算全部候选方向
→ 为多个方向准备目标
→ 计算各方向的可行区间或 LineDomain
→ 全部准备后才开始生成候选
```

这对短预算动作不合适。

特别是 `Search::line()`：后面某条方向分析失败或耗尽预算时，前面完成的分析也可能没有用于产生候选。

### 3.2 修改为 Anytime 候选生成

要求每处理一条方向，就立即尝试产生少量候选，保留本次动作已经找到的最好模型：

```text
输入当前模型、正式覆盖快照、动作预算

选择一个方向
    ↓
进行必要的合法性分析
    ↓
选择与方向相关的少量未覆盖目标
    ↓
立即生成 1–2 个不同合法候选
    ↓
评价实际新增覆盖
    ↓
更新 best_candidate
    ↓
有剩余预算则继续下一个方向

返回 best_candidate
```

任何时间预算结束，都应尽可能返回此前已经找到的合法最佳候选。

不得因为后续方向返回 `BudgetExceeded`，就丢弃前面已经生成的合法模型。

如果错误意味着当前方向不支持分析，跳过该方向。如果已经证明原公式包含当前 LineDomain 根本不支持的运算结构，可以记录公式级 `Unsupported`；不能因一次时间不足就永久禁用 LineDomain。

### 3.3 保持方向公平性

不要重新退化为“第一个方向耗尽全部候选”。

使用分轮的流式考察：

```text
第一轮：每条方向最多完成一个有效候选
第二轮：有预算再分配一个候选
后续：根据当前收益和方向成本继续分配
```

方向本身可以采用已有的分组配额。

要求每种方向来源都具有独立的尝试、成功、耗时和新增覆盖统计。

局部批次应分别限制：

```text
方向准备次数
不同候选评分数量
候选构造总尝试数
动作总时间
```

不要把重复候选计入不同候选的评分额度，但重复尝试仍计入总尝试和时间成本。

### 3.4 目标必须先与方向关联

当前 `TargetManager` 已经具备 `variable_observers` 和变量依赖信息，但主要仍然随机抽目标再排序。

修改为优先从方向影响的变量反向找到相关 AST 观察节点，建立有界目标池。

对于仿射整数表达式，优先计算：

`alpha = coefficient · direction`

对 `alpha != 0` 的数值目标优先进行模命中。

对于 `alpha == 0` 的表达式，如果 Reach 可能变化，则仍可作为观察目标，不能全部删除。

同时保留少量随机/轮转目标，避免仅依赖局部关系而丧失探索能力。

修复 `TargetManager::select()` 的轮转游标：只有真正执行确定性轮转扫描时才增加该游标，确保在足够预算下能够遍历全部节点，而不是长期只访问节点编号的同一模 4 剩余类。

### 3.5 LineDomain 的成本控制

对每条方向先做有限的结构筛查，再进行昂贵的完整可行集合分析。

不要求所有方向都调用完整 LineDomain。

记录：

```text
directions_considered
directions_analyzed
directions_produced_candidates
line_analysis_timeout
line_analysis_unsupported
line_exact_but_no_candidate
line_cross_branch_candidate
time_to_first_valid_candidate
time_to_first_positive_gain_candidate
```

只有实际经过完整合法性和观察条件检验的候选才能输出。

LineDomain 原有精确的交、并、补、无界区间和 Reach 语义不改变。不能为了提速把不连通区间合成凸包，也不能把预算失败报告为不可达。

## 四、问题 3：改进 `polish_candidate()` 的候选和时间预算分配

### 4.1 定位问题

重点检查：

`src/search.cpp::Search::polish_candidate()`

当前默认：

```cpp
candidate_cap = 24;
polish_steps = 6;
polish_seconds = 0.06;
```

但第一次内部 `safe()` 调用可能耗尽全部 24 个候选额度，导致所谓 6 步改进实际上只执行一次候选搜索。

同时 `safe()` 或 `line()` 的准备工作也可能用完整个 60 ms，最终没有时间完成有效比较。

### 4.2 总预算与单步预算分离

为 `polish_candidate()` 保留统一的总预算，但每步只能使用其中一部分。

例如，初始配置可以采用：

```text
最多 6 次内部移动
最多 24 个不同候选
每步优先尝试 2–4 个不同候选
总时间最多 60 ms
```

这些参数必须可配置，并以短实验选择，不应被当成普遍最优值。

如果第一步就发现特别好的模型，可以适当追加预算；如果连续几步没有改善，则提前结束。

每个内部步骤都先生成候选，再评价，再决定下一步，不能预先把剩余预算一次性全部分配出去。

### 4.3 精确保持单模型目标

整个改进期间，正式覆盖集合 `S` 冻结。

始终优化：

`gain(m) = coverage(S ∪ {m}) - coverage(S)`

每一步只接受一个完整合法模型；当前内部模型变化后，重建依赖当前模型的区域、方向可行区间、Reach 和截距。

不能把多个内部模型所覆盖 bit 的并集当作最终一个模型的覆盖。

最终返回本轮找到的最佳完整模型，并保留输入候选作为合法回退。

改进函数也不能直接修改正式覆盖记录。

### 4.4 修复额度修改的实现方式

不要在 `polish_candidate()` 内直接反复修改全局共享的：

```cpp
options.candidate_cap
```

建议将本步剩余额度和时间预算显式作为参数传入候选生成函数，避免异常或提前返回使共享配置残留为错误值。

如果确实需要临时覆盖配置，必须使用可靠的作用域恢复机制，并增加异常路径测试。

### 4.5 检验多步改进是否真正发生

记录：

```text
polish_calls
polish_attempted_steps
polish_accepted_steps
polish_candidates_per_step
polish_improved_models
polish_gain_before
polish_gain_after
polish_elapsed_seconds
polish_stopped_by_time
polish_stopped_by_candidate_budget
```

验收不仅检查 `polish_calls` 数量，还应确认实际改进步数分布、最好单模型收益和收益/时间。

对已无明显改善空间的候选，允许快速跳过 polish；不要为了提高调用次数而增加无价值工作。

## 五、顺便修复两项低成本问题

**第一，空目标包状态。**

检查 `src/global.cpp::Global::repair()`，所有返回路径必须设置明确状态，例如：

```text
sat
unsat
no_target
budget_exhausted
timeout
unknown
```

不能再出现空状态字符串。尤其是未实际发起查询时，不能将其统计成求解失败或 SAT/UNSAT。

**第二，目标筛选的完整状态。**

已证明全局不可达的目标继续排除在后续组包之外，但不要改变正式覆盖分母。

新增目标来源统计，明确区分方向相关目标、Reach 变化目标和随机探索目标。

本轮不新增更复杂的 MaxSMT 或目标冲突优化算法。

# 六、重构实验流程：不再每次完整运行 144 个长任务

第二轮耗时高的主要原因，是每个修改阶段都执行完整长预算消融。

原设计：

`8 个配置 × 9 个实例 × 2 套独立实验 = 144 个正式任务`

每个任务最多 900 秒。这样的流程适合正式论文实验，不适合每次修改后的日常迭代。

必须开发新的分级实验工具。**短实验用于选择算法，最终正式实验才用于报告 900 秒性能；两者不能混淆。**

## 阶段 0：正确性与微基准

修改后先完成：

- C++ 单元测试和 Python 数学参考测试。
- Z3 模型合法性及原评测器差分测试。
- 调度器模拟时间测试。
- 小型流式候选生成测试。
- 多步 polish 的确定性测试。
- ASan/UBSan 回归。

这些测试不需要完整 SMT 900 秒实验。

发现非法输出、覆盖率不一致、方向不合法、超时误判为 UNSAT 等问题时立即停止当前候选版本的性能测试。

## 阶段 1：固定状态下的机制对比（Snapshot Replay）

新增独立的局部实验工具。

从三个开发实例已经保存的样本序列中抽取多个状态：

```text
公式 F
当前模型 m
此前正式输出的覆盖状态 S
剩余覆盖缺口
当前预算
固定随机种子
```

在完全相同的输入状态下，比较旧模块与新模块。

重点比较：

```text
完成第一次合法候选的时间
完成第一次正增益候选的时间
动作总时间
不同合法候选数
最好单模型新增覆盖
最好增益 / 总时间
```

对 `Search::safe()`、`Search::line()` 和 `polish_candidate()` 分别比较。

此工具只比较模块行为，**不能把从同一状态独立调用得到的增益当作完整采样轨迹的性能提升**。

如果缺少求解器内部学习状态，则不能声称已经完整恢复原运行的 SMT 求解器状态。

快照只从开发案例抽取，避免使用评测案例来调参。快照保存源公式哈希、模型、原 AST 覆盖状态、随机种子和版本信息。

实现跨版本的固定快照回归集，后续无需为每次代码修改重新运行 900 秒才能知道局部算法是否改善。

## 阶段 2：短预算端到端筛选

只在已有的三个开发实例上运行候选方法及 A/B 对照。

建议先采用：

```text
实例：3 个开发实例
种子：0、1、2
配置：A/B + 当前候选
每次上限：120 秒
```

总共：

`3 × 3 × 2 = 18 次短运行`

无需再为 5 秒、10 秒、30 秒、60 秒分别启动新进程。保存一个完整 120 秒轨迹，即可从时间戳和样本前缀中还原多个较短截止点的结果。

重点查看：

```text
前 2 / 5 / 10 / 50 / 100 个样本覆盖率
5 / 10 / 30 / 60 / 120 秒覆盖率
每个模块的新增覆盖 / 秒
idle_sleep_seconds
到达不同样本数量的耗时
```

结果至少报告各实例与种子的配对差值，不只输出总体均值。

如果候选方法在模块快测中没有改善、短预算也没有稳定正面趋势，就不要立即投入九例 ×900 秒长实验。先定位原因。

不能仅因为某个种子退步就永久放弃算法；但也不能因为一个开发例的最好结果就自动晋级。

## 阶段 3：中预算检查

只保留短预算中真正值得继续评估的版本。

建议最多比较：

```text
A/B 修复版
本轮最好的一个候选版
```

必要时加入一个关键消融配置，但不要重新加入所有历史阶段版本。

对晋级版本运行 300 秒以内的中预算检查。使用相同的种子集合和运行条件。

六个评测案例应作为冻结后的验证集，不应在每次微调后反复查看并据此修改参数。若需要在九例上进行一次中预算核查，应在核查前冻结当前参数，并明确其不是独立的最终泛化测试。

## 阶段 4：最终 900 秒正式实验

只有候选版本通过前三阶段后，才执行完整 900 秒实验。

保留：

```text
固定时间：900 秒
固定个数：1000 个不同合法样本
```

正式运行记录全部命令、程序哈希、依赖、编译配置、负载、随机种子、超时与完整样本。

继续复用 HighDiv 冻结结果，不自行重跑。

对于新方法与 A/B 的性能差异，尽可能在一致的编译和系统负载条件下做配对；不能把不同并发配置和不同编译等级造成的性能差异全部解释为算法改进。

# 七、重点提速：验证能否从一次采样轨迹计算两类指标

这是减少正式实验数量的重要方法。

当前两套实验分别是：

```text
固定时间组：
最多 900 秒，不限制为 1000 个样本

固定个数组：
最多 900 秒，达到 1000 个样本就停止
```

对于相同公式、算法与种子，如果样本数量上限在达到 1000 前不影响算法选择和输出序列，那么一次固定时间运行可以得到：

- 到 900 秒时的覆盖率；
- 前 1000 个不同合法样本的覆盖率；
- 到达第 1000 个样本的时间。

没有达到 1000 时，严格固定数量结果仍标记为未完成。

### 必须先进行前缀一致性审计

检查现有代码中 `-n` 的所有使用位置，确认除了达到数量后停止，不会在前 1000 个样本期间改变：

```text
随机数使用
调度决策
候选选择
覆盖更新
求解器预算
种子管理
输出筛选
```

再用相同配置、种子和受控运行条件，比较短时间内的 `-n 1000` 与 `-n 4294967295` 运行，确认前缀行为符合预期。

由于算法含实际时间预算，单独重跑的样本序列未必逐位一致，不能仅凭两次不同时间运行的随机轨迹差异断言 `-n` 影响算法。代码路径审计与受控测试需要结合进行。

通过后，在**开发迭代中**采用统一时间轨迹：

```text
运行一次不以 1000 为数量限制的采样
    ↓
根据真实输出顺序构造时间曲线
    ↓
截取前 k 个不同有效样本
    ↓
同时报告时间与样本数指标
```

**不得对前 k 个样本重新排序，也不得事后从全部 900 秒输出中选择最佳 k 个来冒充在线前缀。**

如果最终论文实验需要两套独立的随机运行，可在最终阶段单独补做。日常开发不需要反复进行这项重复计算。

这样，原来的八个配置、九个实例、两套协议共 144 次任务，在单轨迹双指标的实验定义成立时，可以减少为 72 次；再通过筛选只保留两个配置，长预算任务可缩减到 18 次。

注意：这是减少实验总工作量，不意味着同样 144 次 900 秒任务能够在不增加计算资源的情况下自动完成得更快。

## 八、不增加硬件的其他实验加速措施

### 8.1 根据实际吞吐选择并发数，而不是固定使用 15

目前的 15 个并行采样进程不一定是最快配置。

在开发实例上分别检查较低和较高的并发度，例如：

```text
3、6、9、12、15
```

记录：

```text
单位墙钟完成的有效工作量
CPU 利用率
峰值内存和总 RSS
上下文切换
CPU throttling（如存在）
单个任务的平均运行速度
```

选择实际总吞吐更高、内存和系统负载稳定的配置，而不是简单选择并发数最大的配置。

不同并发设置下的覆盖率结果不能直接视为同等资源条件下的严格性能比较。最终 A/B 与候选方法必须保持一致的资源环境。

### 8.2 开发期不重复完整审计所有历史结果

对冻结的基线使用已有审计结果和哈希缓存。

新增开发运行应：

- 保留所有模型的采样器内部合法性检查；
- 对机制测试和短实验做独立合法性复核及覆盖差分；
- 在候选晋级前进行完整审计；
- 最终正式运行对全部样本进行独立审计。

只改变分析脚本时，允许直接复算已保存的模型和时间戳，不重新运行采样器。

审计缓存必须绑定输入公式、完整模型数据、评测器版本和指标定义的哈希，不能仅按文件名跳过验证。

### 8.3 不要每次迭代都重新打包全部原始数据

开发阶段先写入固定目录：

```text
results/round3_dev/
results/round3_snapshots/
results/round3_screen/
results/round3_confirm/
```

避免覆盖历史结果。

只在最终正式版本完整审计结束后，再生成大型 `raw.tar.gz`、完整证据包和最终报告。

不要删除失败运行的诊断材料。

### 8.4 尽量复用构建结果

使用增量 CMake 构建。源码或依赖不变时，不重新构建冻结 Z3。

记录实际二进制和源码哈希。若核心代码未变化，只修改分析报告或绘图程序，不触发采样运行。

## 十、最终验收与交付

请按顺序提交：

**提交 1：调度修复。** 修复软冷却造成的无效等待，完善真实时间核算。

**提交 2：流式局部生成。** 修改 `safe()`、`line()`，实现按方向分析后立即生成候选，保证预算结束时能保留已有最好合法模型。

**提交 3：多步协同改进。** 调整 `polish_candidate()` 的单步预算、总预算和配置作用域；修复目标轮转扫描和空状态记录。

**提交 4：快速实验框架。** 实现固定状态微基准、短预算分级筛选、统一时间轨迹提取前 k 样本指标、审计缓存和实验成本报告。

每个提交完成后运行相应回归测试，不必立即做九例完整长跑。

最终报告分开回答：

1. 调度器是否真正消除了无效等待？原来的大量未分项时间去了哪里？
2. `safe()` 和 `line()` 是否缩短了首次合法候选、首次正增益候选的产生时间？
3. polish 是否真正形成更多有效的多步移动，且最终单模型覆盖收益超过额外成本？
4. 哪些模块从新增覆盖/秒、前 k 样本覆盖和最终固定时间覆盖三个层面产生实际收益？
5. 本轮机制测试、短实验和正式长实验分别消耗多少 CPU 时间、墙钟时间与审计时间？
6. 最终是否同时改善相同时间和相同样本数下的覆盖？如果没有，明确指出收益与退化原因。

**不以“新机制触发了多少次”作为性能成功标准。** 如果调度闲置已经修复、候选准备已经流式化、polish 已经能执行真正的多步改进，但效果仍然不明显，应保留证据并报告算法主线的剩余局限，而不是继续无依据地叠加启发式。

本轮最终优先级为：

**正确性不退步 → 去除无效计算时间 → 提高局部候选产出效率 → 提升单样本增益 → 少量长预算确认。**
