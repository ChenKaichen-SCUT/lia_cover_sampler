# 第九轮指引：修复宏观查询预算与备选选择，验证真实采样收益

## 1. 修改基点、研究目标与不变项

以 `ChenKaichen-SCUT/lia_cover_sampler` 的冻结提交 `af9b2c6` 为基点，新建分支。

本轮目标是：

> **让宏观生成器正确识别限时失败，给值得重试的查询提供实际可用的连续预算，同时避免在少数困难备选上反复浪费尝试；然后验证这些修补是否产生及时、合法且具有真实新增覆盖的模型。**

保留第八轮原始结果和“停止扩大实验”的决定，不事后修改其计分或晋级规则。本轮采用新的、预先冻结的诊断和验证协议。

不重跑 HighDiv，不重放全部 291,989 个模型，不启动 900 秒实验，不修改覆盖指标、原始 AST 或模型合法性标准。不启用旧变量块扩张、polish、准备复用或新的 MaxSMT 方法。

先完成针对性的诊断和代码修补，再决定是否进入短在线实验。**正确性、机制是否可用、整体性能是否改善，必须分开验收。**

## 2. 先查清旧失败记录，不将 99 次 Unknown 一概解释为超时

### 2.1 建立查询级诊断表

读取第八轮已有：

```text
results/round8_macro/online_30s/
results/round8_macro/mechanism_400ms/
```

按原始查询记录、会话日志及源码，恢复以下信息：

```text
公式、种子、会话、轮次、查询编号
选择组与备选身份
请求求解时限
实际设置的求解时限
solver.check 的耗时
整个查询的耗时
父动作与会话的剩余预算
原始返回状态与 reason_unknown
是否存在外部中断
该备选此前的尝试次数及结果
```

历史日志未保存的字段必须标为 `unknown`。不能因为默认值是 50 ms，就把所有历史调用的实际时限都补写为 50 ms。

当前机制日志确实存在宏观查询 `unknown/canceled`，而同批普通探索将类似结果记录为 `timeout/canceled`；这是需要核对的差异，不是直接证明两者原因完全相同。

### 2.2 用已有合法模型检查备选的可达性

只对本轮相关的离散选择公式和备选，复用已有合法历史模型进行具体求值，不重新扫描全部无关实例。

对于备选条件 \(P_{g,j}\)，若找到历史完整赋值 \(w\) 满足：

$$
F(w)\land P_{g,j}(w),
$$

记录模型身份、来源哈希、备选身份和验证结果，标记为 `WITNESSED_FEASIBLE`。

没有找到见证时，只能标记 `NO_WITNESS_IN_POOL`，不能标为不可满足。

额外核对见证是否不同于当前种子、是否能增加当前覆盖。**“备选可满足”“能产生不同模型”“能增加覆盖”是三个不同的性质。**

这份历史见证表只供离线诊断使用。正式生成器不得读取见证赋值、历史模型池或由这些模型提供的答案。

### 2.3 冻结一个小诊断集合

先按既有查询记录和结构身份，固定最多六个备选：兼顾反复失败的已查询备选和尚未查询的备选，不按新实验表现筛选。

然后给它们附上历史见证标签。若集合中没有任何已知 SAT 备选，可以另外加入至多两个有历史见证的正对照，并明确标为**已知可行性诊断**，不计入算法性能样本。

## 3. 修复状态分类与超时适配

### 3.1 具体代码位置

重点修改：

```text
src/macro_choice.cpp
    MacroChoiceGenerator::query_choices()

src/control.cpp
    SolveBudgetState::observe()

include/core.hpp
    查询状态与预算反馈结构
```

当前宏观分类仅检查 reason 是否含 `"timeout"`，否则归为 Unknown；而 `SolveBudgetState::observe()` 在 Timeout 下增加时限，在 Unknown 下不增加。 

### 3.2 原始状态与退出原因分开保存

不要简单执行：

```cpp
if (reason == "canceled")
    status = Timeout;
```

新增统一的结果解释接口，输入至少包含：

```cpp
struct QueryExitEvidence {
    std::string raw_reason;
    unsigned actual_timeout_ms;
    double check_seconds;
    bool external_interrupt;
    bool session_deadline_reached;
    bool action_deadline_reached;
    bool resource_limit_enabled;
};
```

保存求解器原始返回值和原因，再给出用于控制的退出分类：

| 情况 | 控制处理 |
|---|---|
| 明确外部中断 | 停止，不继续重试 |
| 会话总截止已到 | 结束会话，不增长预算后再启动查询 |
| 明确资源耗尽 | 单独记录，增加 timeout 不视为解决办法 |
| 明确本次查询超时 | 允许预算升级 |
| `canceled` 且耗时接近本次实际时限、没有外部取消证据 | 标为“疑似局部限时取消”，允许受限升级，但保留推断标志 |
| 原因不足或其他 Unknown | 保留未知，不产生逻辑结论 |

判断耗时应使用 **`solver.check()` 自身的时间**，不能将前面的目录、约束构造或日志耗时用于推断求解器是否触及 timeout。

无法可靠识别时，宁可保留不确定性，也不能伪造确定原因。所有这些非证明状态都不能进入不可达缓存。

### 3.3 预算升级应针对实际尝试

首版使用统一、可配置的重试级别，例如：

```text
50 ms → 200 ms → 1000 ms → 2000 ms
```

这是新实验的固定初始策略，不宣称最优。

同一备选因局部时限失败后，后续重试可以进入更高一级；没有真正获得该级别时间，就不能记作“已尝试过 1000 ms”。

记录：

```text
requested_timeout_ms
granted_timeout_ms
actual_check_seconds
budget_clip_reason
retry_level_before / after
classification_evidence
```

若实际时限因会话剩余预算被截短，记录为截短尝试，不能按完整级别的失败更新状态。

## 4. 修复外层时间片，避免“时限增长了，实际仍只能跑很短”

当前在线流程每轮最多 1 秒，广泛阶段最多约 40%，内部又把约 80% 用于查询。因此，即使自适应时限提高到 1000 ms，原嵌套预算仍可能把实际执行截到约 320 ms 或更短。 

### 4.1 不增加总预算，改变预算的分配单位

先在机制实验中让普通探索与宏观探索拥有相同的会话总预算，但允许某一次调用使用较长的连续时间。不要继续把每次尝试强制塞进同样的小时间片。

在线集成时，把广泛探索份额按**会话累计成本**管理，而不是只按“每个一秒轮次的 40%”管理。允许一个必要的较长广泛动作消耗多个原短时间片的额度，其成本从同一会话预算中扣除。

两个配置使用相同的预算管理器和相同上限。不能只给宏观配置新增长调用机会。

### 4.2 分开查询预算与交付预算

每次启动求解前，确认剩余预算足以容纳：

$$
\text{请求的求解时间}
+
\text{必要验证和输出预留}.
$$

不足时，可以明确地缩短本次实际时限，或者选择另一项可完成的工作；不能假装已执行完整升级，也不能为了攒额度让程序无意义休眠。

后续查询超时，必须返回已有的及时合法候选。已经完成的检查点不能因为继续搜索而丢失；尚未完成最终验证或写出的模型不能倒签时间。

### 4.3 暂不同时改求解器策略

本轮先保持原求解器类型、主要参数和约束表达方式不变，避免把状态分类、预算、求解器更换同时混在一起。

另记录一个事实：首次求解、宏观求解器和普通探索求解器是否分别初始化，哪些学习状态被丢弃。**已有种子不代表新的求解器已经获得原求解器的搜索状态。** 这一点先作为诊断，不在本轮自动加入复杂的求解器共享改造。

## 5. 改进备选选择：广泛试探与有依据的深入重试并存

### 5.1 分开“访问过”与“尝试过”

修改 `ChoiceAlternative`，新增独立运行状态，例如：

```cpp
struct AlternativeAttemptState {
    uint64_t attempts = 0;
    uint64_t sat_count = 0;
    uint64_t timeout_like_count = 0;
    uint64_t unknown_count = 0;
    double cumulative_seconds = 0;
    unsigned retry_level = 0;
    uint64_t last_attempt_order = 0;
    uint64_t eligible_after_order = 0;
};
```

原 `visits` 继续表示正式样本访问情况，不能因为一次失败查询就增加它。

当前排序主要看正式访问次数和相关算术范围。没有输出新模型时，困难备选的优先级可能长期不变，导致反复查询。第八轮每个种子只查询了 11–13 个不同备选，部分备选重复 5–6 次。 

### 5.2 使用简单的双队列，不增加学习型调度器

维护两类机会：

**新备选队列：** 当前模型尚未满足、未被证明不可行、此前尚未查询的备选。

**升级重试队列：** 曾因局部时间限制未完成、允许更高预算重试的备选。

首版可以固定采用“优先完成两次新备选尝试，再允许一次升级重试”的顺序；队列为空时使用另一队列。不要通过实验结果反复调整比例。

同一备选失败后，至少让其他备选获得机会。排序中的算术影响范围只作次级依据，不能再次让少数大范围、难求解目标长期垄断队列。

每个备选在一个短会话内最多完成预设的四个预算级别，不无限升级。一般 Unknown 不自动视为值得持续加时，只允许有界延后重试。

### 5.3 仍以完整公式协调变量

宏观查询继续采用：

$$
F(x)\land P_{g,j}(x),
$$

不重新加入“其余变量保持旧值”的限制。

优先尝试当前模型不满足的真实备选，避免将当前配置原样求回。对于非互斥组，不能凭辅助标签认定发生了模式变化。

本轮首版关闭“两组同时强制切换”的自动扩展，先把**单个选择切换**求稳。当前真实查询连单备选 SAT 都没有，先增加组合只会使原因更难解释。组合功能保留为非默认选项，不删除历史实现。

## 6. 对无适用结构的公式，尽量透明回退

第八轮的 Bromberger 和 convert 没有当前提取器支持的选择组，宏观查询实际上不触发；因此，它们主要用于检查回退成本与兼容性，而不是证明宏观收益。

修改初始化和分发：

```cpp
if (catalog.groups.empty()) {
    // 直接走与 plain 相同的广泛探索路径
}
```

没有选择组时，不额外构造宏观求解器，不执行备选排序，不消耗普通探索或微观模块的随机数，不经过不必要的包装层。

目录识别本身的成本仍须计入，不能把它藏到计时之外。

同样，宏观队列暂时没有可用备选时直接回退通用探索，不休眠，不把“目录耗尽”解释为原公式解空间耗尽。

增加受控回归：给定相同初始状态、随机数和模拟时钟，无适用选择组时，两条执行路径应产生相同的查询决策。真实限时运行仍可能受系统调度影响，不能据此承诺逐模型完全一致。

## 7. 必须完成的回归与诊断验证

优先使用模拟时钟、可注入求解结果验证控制逻辑，避免靠机器运行快慢制造测试条件。

| 测试 | 验收要求 |
|---|---|
| `canceled` 与局部时限吻合 | 保留原始原因，产生有依据的预算升级 |
| 外部取消 | 立即停止，不能误当局部超时继续重试 |
| 全局截止 | 不再启动下一次查询 |
| 资源耗尽 | 不把加时当作恢复资源 |
| 请求 1000 ms、父预算只剩 100 ms | 明确记录截短，不记为完整 1000 ms 失败 |
| 同一备选不断超时 | 其他未查询备选仍获得机会 |
| 一个备选需要更长预算 | 升级重试能实际获得连续时间，不被旧 320 ms 上限卡住 |
| 无选择目录 | 不构造多余宏观求解器，回退行为一致 |
| 单备选 UNSAT 与组合 UNSAT | 只在正确作用域缓存 |
| 及时见证后超时 | 原及时见证保留，迟到模型不计分 |

构造一个模拟查询：低于 200 ms 返回局部限时取消，达到 200 ms 返回手写合法模型。它用于验证控制链，不作为真实性能证据。

真实语义测试继续覆盖成组取值、等式协同、非互斥 OR、负数与大整数、完整赋值、正式覆盖不被内部候选修改，以及原评测器差分。

非法模型、覆盖不一致、错误 UNSAT 缓存和时间倒签属于立即停止条件，不因性能结果好而容忍。

## 8. 分阶段实验：先排故，再验证机制，最后才测在线效果

### 阶段 A：少量备选的求解能力诊断

使用第 2 节固定的小集合、两个 solver seed，对相同查询分别给出：

```text
50 ms、200 ms、1000 ms、2000 ms
```

各预算点使用明确的初始求解器生命周期。不要让一个点免费继承前面预算点的搜索工作；若另外测试递增重试会话，必须将之前全部成本一起计算，并与独立调用结果分表。

记录约束构造、`check()`、模型补全、验证及总耗时。请求时限只是 `check()` 上限，完整动作成本可能更大，不能混淆。

已知 SAT 查询只是诊断正对照：其作用是检验“确实可满足却没求出来”的原因，不得用历史见证指定变量值、提供模型提示，或把它当作盲目采样的成功率。

这一阶段回答：

> 分类修复后预算是否实际增长？较长连续预算能否找到先前短调用找不到的模型？是否仍然完全没有实际进展？

不凭一条成功查询宣称算法更快。

### 阶段 B：同预算的连续候选生成

通过正确性验证后，在现有 SMT_random 的两个开发快照上比较三个配置：

| 配置 | 内容 |
|---|---|
| `plain_fixed` | 普通探索，使用修正后的公共预算管理 |
| `macro_budget_fixed` | 原备选排序，只修复分类与预算 |
| `macro_fair_retry` | 再加入新备选／升级重试队列 |

采用两个快照、三个既定种子，共 **18 个短会话**，每个会话统一 **10 秒总预算**。

种子先正式计入覆盖：

$$
S_0=S\cup\{m\}.
$$

之后每次提交模型立即更新覆盖。不得再按冻结的 \(S_0\) 独立评分后相加。

双方使用相同的单查询最大时限、验证口径和总预算。普通探索也允许较长连续调用，不能拿“新方法可跑 2 秒”对比“基线被限制在 50 ms”。

公式加载、快照恢复和引擎初始化按每个会话一次计入；会话内不反复重收初始化成本，也不将初始化免费排除。

主要报告：及时不同模型数、正增益模型数、真实累计覆盖、前若干新样本覆盖、首次正收益时间、不同备选尝试数、重复尝试成本，以及宏观见证和普通回退见证的来源。

三个配置用于区分**预算修复有效**和**备选选择有效**。不要再扩成八种配置。

### 阶段 C：有机制证据后，才执行短在线对照

满足下一节的机制条件后，再比较 `micro_plain` 与修补后的 `micro_macro`，保持微观机制、目标窗口和覆盖更新不变。

使用三个既定开发案例、三个种子、两个配置，共 **18 次 30 秒会话**。从首次求解开始计时，初始模型计入样本，保留所有无输出和失败运行。

普通和宏观版本的配对任务必须安排在同一批受控负载中。建议按完整配对或三配置组分批启动，最多六路并发；不要再次让一个配对跨越“满负载首波”和“低负载末波”。不重新进行 75 次并发校准。

新的运行条件必须记录，不能与旧 15 路历史时间结果混为同条件比较。独立审计在采样结束后执行，避免争抢采样资源。

## 9. 修改晋级规则：按适用性分层，而不是要求不适用案例也改善

第八轮真正适用的开发案例只有 SMT_random。因此，本轮**机制阶段不再要求三个开发案例中至少两个改善**；但不能因此降低最终通用性能要求。

### 机制阶段继续条件

需要在真实适用结构上，至少两个 solver seed 出现及时、合法、不同的宏观候选，并且有真实新增覆盖。进一步进入在线比较，还需要同预算下相对于普通探索出现可重复的正面信号，例如：

- 累计覆盖更高；
- 达到同等覆盖更快；
- 相同数量候选的覆盖更高，而总体时间代价受控。

只出现 SAT、不增加覆盖，不算性能进展。仅历史见证辅助挑出的正对照成功，也不能单独满足这一条件。

### 在线阶段判断

适用实例看收益；不适用实例看回退开销和是否出现可解释的退化。一次受队列负载干扰的均值下降是警报，不自动当成宏观机制的因果负面结论。

如果在唯一适用实例上看到稳定信号，可以继续选取**新的、有同类结构且未用于调参的真实实例**验证。选择规则必须依据结构和来源预先冻结，不按跑出来的效果挑案例。多个种子和多个快照仍然不能冒充多个独立公式。

### 停止与暂缓的区别

| 结果 | 处理 |
|---|---|
| 正确性或计分失败 | 立即停止性能实验，修复后重验 |
| 修补后仍全部限时未完成 | 记录“在已测试预算内证据不足”，不自动扩大到长实验 |
| 有 SAT，但新增覆盖低、成本明显高于普通探索 | 当前实现不晋级 |
| 只在一个适用实例有稳定收益 | 允许有界的适用实例扩展，不宣称通用优势 |
| 多个独立适用实例有收益，回退成本可控 | 再规划综合评测 |

新协议在运行前冻结。不得看完结果后修改成功标准，也不通过不断增大时限直到出现正结果来选择性报告。

## 10. 交付内容与最终必须回答的问题

建议分为三个独立提交：

**提交一：失败原因与预算修复。** 包含历史查询复核、可行性见证索引、状态分类、实际预算记录和回归测试。

**提交二：公平备选与升级重试。** 包含独立尝试状态、有限队列、透明回退和对应消融开关。

**提交三：同预算机制实验及条件满足后的短在线实验。** 保留完整输入、模型、查询、时间戳、失败、归档哈希和重放命令。

最终报告必须回答：

1. 过去的 `unknown/canceled` 中，哪些有证据支持限时取消，哪些仍不能判断？
2. 修补后，请求的较长预算是否真正到达 `solver.check()`，还是仍被外层截断？
3. 新队列是否增加了不同备选的探索，同时避免无意义地重复短查询？
4. 是否产生了真实宏观 SAT、真实新模型和真实新覆盖？三者分别是多少？
5. 改善来自预算修复，还是备选选择？普通探索在同样预算管理下是否也得到同等改善？
6. 不适用公式是否透明回退，新增初始化和管理成本是多少？
7. 当前结果支持继续验证、仅支持排故完成，还是已经显示该实现不值得成本？
